Frequently Asked Accessibility Questions

Core standards and engineering best practices for building inclusive web applications.

WCAG 2.1 Level AA encompasses 50 success criteria structured around four foundational principles: Perceivable, Operable, Understandable, and Robust (POUR). Essential benchmarks include:

  • Minimum text color contrast ratio of 4.5:1 for normal text and 3:1 for large text and UI components (SC 1.4.3, 1.4.11).
  • Complete operability via keyboard without traps or reliance on pointer gestures (SC 2.1.1, 2.1.2).
  • Clear, visible keyboard focus indicators with adequate contrast against adjacent colors (SC 2.4.7).
  • Valid document landmarks and heading hierarchies enabling swift assistive technology navigation (SC 1.3.1).
  • Predictable, accessible forms with associated labels, hints, and error notifications (SC 3.3.1, 3.3.2).

The First Rule of ARIA states: "If you can use a native HTML element or attribute with the semantics and behavior you already require, then do so instead of re-purposing an element and adding an ARIA role, state or property."

Native elements like <button>, <a>, <details>, and <dialog> have built-in keyboard behavior, focus management, and accessibility tree representation across all operating systems and screen readers. Misusing ARIA roles on arbitrary <div> elements frequently introduces silent accessibility bugs.

ARIA live regions (aria-live="polite" or aria-live="assertive") notify assistive technologies when content updates dynamically without requiring a page reload or shifting the user's current keyboard focus.

In this portal, live regions announce search filter result counts and form validation updates, ensuring blind and low-vision users remain fully aware of background data changes.
